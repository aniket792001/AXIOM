# Contributing to Axiom & SCORE Engine

Thank you for your interest in contributing to **Axiom**! We are building an enterprise-grade, zero-hallucination, self-correcting RAG platform. 

Every line of code and prompt template in this repository is designed around one core philosophy: **Epistemic Humility**. The engine must never bluff, never guess, and always provide verifiable evidence.

---

## 🧭 Code of Principles

1. **Never Mask Failure**: We do not write prompts or fallback logic that generates plausible-sounding filler when retrieval fails. A clean, diagnostic refusal is always superior to a hallucinated answer.
2. **Deterministic Citations**: Any answer generated by the engine must cite verifiable chunk IDs.
3. **Strict Typing**: All nodes, state models, and API boundaries must use Python type hints (`TypedDict`, `pydantic.BaseModel`).
4. **Decoupled Prompts**: Prompts must never be hardcoded into Python logic. Store them in `src/axiom/core/prompts/`.
5. **Continuous Evaluation**: A PR that improves subjective answers but lowers the **Ragas Faithfulness benchmark** ($\ge 0.95$) will not be merged.

## 🛠️ Local Development Setup

### 1. Prerequisites
* Python 3.10 or higher
* [uv](https://github.com/astral-sh/uv) (recommended) or `pip`
* Git

### 2. Initializing Environment
```bash
# Clone the repository
git clone https://github.com/your-org/axiom-rag.git
cd axiom-rag

# Create virtual environment
python -m venv .venv
source .venv/bin/activate  # On Windows: .venv\Scripts\activate

# Install dependencies in editable mode with development tools
pip install -e ".[dev]"
```

### 3. Setup Pre-commit & Linters
We use **Ruff** for lightning-fast formatting and linting:
```bash
# Format code
ruff format .

# Check linting
ruff check .

# Run type checker
mypy src/
```

## 🌿 Branching & Git Workflow

We follow standard GitHub flow:
1. Fork and create a feature branch off `main`:
   ```bash
   git checkout -b feat/hybrid-retriever-bm25
   ```
2. Branch naming conventions:
   * `feat/` — New feature or node capability (e.g., `feat/reranker-integration`)
   * `fix/` — Bug fix or error handling (e.g., `fix/hallucination-grader-parser`)
   * `eval/` — Evaluation dataset or benchmark script (e.g., `eval/sec-10k-golden-dataset`)
   * `docs/` — Documentation updates (e.g., `docs/api-streaming-reference`)
   * `refactor/` — Code refactoring without behavior change

---

## 📝 Commit Message Convention

We follow [Conventional Commits](https://www.conventionalcommits.org/):
```
<type>(<scope>): <short description>

[optional body]
[optional footer]
```

**Allowed Types:**
* `feat`: A new feature for the engine or API
* `fix`: A bug fix
* `docs`: Documentation only changes
* `style`: Code style changes (formatting, whitespace)
* `refactor`: Code changes that neither fix a bug nor add a feature
* `perf`: Performance optimizations
* `test`: Adding or updating tests / benchmarks
* `chore`: Build process or auxiliary tool changes

**Example:**
```bash
git commit -m "feat(grader): add structured binary output for document relevance"
```

## 🧪 Testing & Evaluation Requirements

Before opening a Pull Request:
1. **Unit Tests**: Ensure all unit tests pass:
   ```bash
   pytest tests/unit/
   ```
2. **Integration Tests**: Verify state machine loops:
   ```bash
   pytest tests/integration/
   ```
3. **Automated Evals**: If your change modifies prompt templates, grading thresholds, or rewriter logic, run the benchmark suite:
   ```bash
   python evals/run_evals.py
   ```
   *Your PR description must include the before-and-after Ragas scores (Faithfulness, Relevance, Precision).*

---

## 📬 Submitting a Pull Request (PR)

When opening a PR, ensure:
* [ ] Description clearly explains the motivation and technical changes.
* [ ] All tests pass locally.
* [ ] Type checking (`mypy src/`) passes with zero errors.
* [ ] Documentation is updated if API signatures or prompt contracts changed.
* [ ] Any new environment variables are documented in `.env.example`.

Thank you for helping make Axiom the most reliable RAG platform in production!
